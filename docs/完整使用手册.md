# Vaultwarden 1Panel Backup Manager 完整使用手册

**版本 1.5.0**

**平台：Ubuntu / Debian + 1Panel + Docker + Vaultwarden SQLite**

---

## 1. 项目职责

1Panel 负责 Vaultwarden 应用、Docker、域名、HTTPS 证书和反向代理。本工具负责检测正确的容器与 `/data` 数据目录、创建一致性备份、age 加密、GitHub/WebDAV 同步、恢复、诊断和 systemd 自动调度。

本工具不会安装/升级 Docker、1Panel 或 Vaultwarden，不会配置域名、HTTPS 或反向代理。

## 2. 系统要求

- Ubuntu / Debian，使用 systemd。
- Docker 由 1Panel 管理，当前 Vaultwarden 容器运行正常。
- Vaultwarden 容器内数据路径 `/data` 映射到主机目录。
- 使用 SQLite 数据库，主机数据目录内存在非空 `db.sqlite3`。
- root 权限。
- GitHub 源码仓库与备份存储分开。备份存储可以选 GitHub Private 或 WebDAV HTTPS 目录。

不支持 MySQL/PostgreSQL 外部数据库，也不适合非 `/data` 自定义布局。

## 4. 下载与启动

```bash
sudo apt update
sudo apt install -y git
sudo git clone https://github.com/OmenTwwnmfm/vaultwarden-1panel-backup-manager.git /opt/vaultwarden-1panel-backup-manager
cd /opt/vaultwarden-1panel-backup-manager
sudo bash ./run.sh
```

必须在 SSH 交互终端运行。首次运行在菜单 `[01]` 配置。源码仓库为 Public，可匿名 HTTPS 克隆；只有数据备份仓库需要 SSH Deploy Key 写入权限。项目必须位于 root 所有且不可被其他用户修改的目录中，推荐使用 `/opt`；启动器会拒绝从用户可写路径以 root 执行项目脚本。

## 6. 首次配置：菜单 01

向导会依次进行：

1. 检查 Docker 命令可用性。
2. 搜索名称或镜像中包含 Vaultwarden 的容器。多个候选容器时要求人工选择。
3. 使用 `docker inspect` 读取容器内 `/data` 对应的主机路径。
4. 确认主机路径存在，且其中有非空 `db.sqlite3`。
5. 检查并按需安装 age、sqlite3、python3、logrotate 等备份工具。选择 GitHub 时另需 git 和 OpenSSH，选择 WebDAV 时不需要 GitHub SSH 依赖，不会安装 Docker。
6. GitHub 目标创建 SSH Deploy Key 并显示公钥，或 WebDAV 目标输入 HTTPS 目录与应用密码并测试读取。
7. 使用旧 age 公钥或首次生成 age 密钥。若已有历史备份，必须输入创建历史备份时的原公钥。
8. 设置本地备份目录、保留天数和 GitHub 文件大小上限；GitHub 目标另设置 Git 工作目录。
9. 显示配置摘要；核对容器、镜像、`/data` 主机路径、备份目标和 age 公钥后输入 `yes`（不区分大小写）。
10. 保存 `/etc/vaultwarden-backup.conf`（权限 600）并安装后台脚本。

age 公钥可以保存在服务器。age 私钥必须离线保存至少两份并验证可读；日常自动备份不需要把私钥留在 VPS。

## 7. 立即备份：菜单 02

执行前会再次自动发现容器，并用已经确认的 `/data` 主机路径匹配实例。若 1Panel 重建应用导致容器随机后缀变化，但数据路径不变，会更新容器名；若数据路径发生改变或存在多个无法唯一确定的候选项，则停止操作并要求重新配置。

执行过程：

1. 检查容器状态、数据路径、SQLite 文件和可用磁盘空间。
2. 短暂停止 Vaultwarden，保证整个 `/data` 快照一致。
3. 执行 SQLite quick_check。
4. 打包整个 `/data`，通过 age 公钥加密。
5. 加密快照创建后立即尝试启动 Vaultwarden。
6. 验证密文非空、大小、age 文件头和 SHA256。
7. 生成脱敏部署清单并单独 age 加密。
8. 将数据备份、部署清单及校验文件上传到当前目标。
9. GitHub 目标重试临时推送错误并核验分支提交 ID，WebDAV 目标回读文件并核验 SHA256。
10. 记录备份结果并发送可选通知。

请定期使用离线私钥通过菜单 `[05]` 验证历史备份，或通过 `[09]` 进行隔离演练。

## 8. 检查环境（菜单 03）

路径摘要列出本地加密备份目录、GitHub 备份仓库和分支、GitHub 本地工作目录，以及 WebDAV 实际使用的 `vbm/` 目录。保留原始配置时，WebDAV 的实际目录会根据已有 URL 自动计算。

菜单还显示 age 恢复私钥的默认路径、GitHub SSH 私钥路径及文件是否存在，以及备份配置和 WebDAV 凭据文件的位置。age 私钥可离线保存，恢复时可输入临时提供的原私钥路径。摘要仅显示路径信息，私钥和凭据内容保持私密。

检查当前容器与配置中记录的主机数据路径是否匹配，检查 `db.sqlite3`、age 公钥和当前备份目标连接。GitHub 会检查 SSH 私钥与仓库读取，WebDAV 会测试目录读取。检测到容器名变化时会按原 `/data` 路径更新记录。

```bash
journalctl -u vw-backup.service -n 100 --no-pager
```

## 11. 同步后台脚本（菜单 22）

从完整项目目录运行更新，输入 `yes` 确认。更新后可用 `[03]` 检查环境，再用 `[05]` 验证历史备份。

## 12. 验证历史备份（菜单 05）

从 GitHub、WebDAV 或本地目录选择历史 `.tar.gz.age`，在输入原 age 私钥路径后执行：

- SHA256 校验。
- age 实际解密。
- gzip/tar 归档读取与安全路径检查。
- 检查 `db.sqlite3` 是否存在且非空。
- 对解密数据库执行 SQLite `PRAGMA quick_check`。

验证完成后，临时解密文件应在受限临时目录中清理。私钥建议从离线介质临时提供，测试完成后删除 VPS 上的私钥副本。

## 13. systemd 自动备份（菜单 14–17）

菜单 `[14]` 可设置 GitHub 或 WebDAV 目标，并选择每日、每周日或每月 1 日的 VPS 本地执行时间。默认每日 05:20。安装以下文件。

- `/etc/systemd/system/vw-backup.service`
- `/etc/systemd/system/vw-backup.timer`

Timer 使用 `Persistent=true`，VPS 关机错过计划后，在下一次启动时补执行。使用 `[15]` 查看状态、`[16]` 暂停、`[17]` 恢复。

常用命令：

```bash
systemctl list-timers --all | grep vw-backup
systemctl status vw-backup.timer
systemctl start vw-backup.service
journalctl -u vw-backup.service -n 100 --no-pager
```

## 14. 通知（菜单 18）

支持 Telegram、ntfy 和通用 Webhook，可分别开关成功/失败通知。凭据保存在 root 专用配置文件中，权限 600。通知发送失败只产生 WARN，不会把已经成功的备份改判为失败。

不要把 Bot Token、ntfy Token 或 Webhook URL 发到公开 Issue，也不要放进 README。

## 15. 更新前保护（菜单 19）

在 1Panel 更新 Vaultwarden 前，先运行一份完整备份。只有工作器返回成功且当前备份目标的远端核验通过，才建议继续应用更新。版本更新仍由 1Panel 执行，本工具不会升级 Vaultwarden。

## 16. 系统诊断（菜单 20）

生成脱敏诊断报告，默认目录：

```text
/var/log/vaultwarden-backup-diagnostics/
```

文件名类似 `diagnosis-YYYYMMDD-HHMMSS-PID.txt`，权限为 600，目录权限为 700。报告包括：

- 系统命令可用性（Docker、age、Git、SQLite 等）。
- 配置存在状态和非秘密配置字段。
- Docker 容器列表与当前 Vaultwarden 目标发现结果。
- 数据目录磁盘空间、目录大小、数据库大小和 quick_check。
- systemd timer 与最近服务执行状态。
- 最近备份结果摘要和日志尾部。

报告不会输出 age 私钥、SSH 私钥、Bot Token 或 Webhook Token。分享报告前仍应人工检查主机名、路径、域名和 GitHub 用户名等环境信息。

## 17. 性能监控与执行耗时分析（菜单 07）

性能记录保存在：

```text
/var/lib/vaultwarden-backup/performance.tsv
```

文件由 root 创建，权限为 600，目录权限为 700。性能记录不包含密码、Token、私钥或数据库内容。

v1.4.3 对性能记录进行了细分，v1.4.4 对启动后的健康探测进一步细分，v1.4.5 增加人工等待与服务停机窗口记录。旧版本聚合记录仍保留并标注为“旧版”；升级不能追溯拆分此前已经产生的单一聚合时长。

目前记录以下阶段：

**备份：** 容器发现与预检查、部署清单生成、停止 Vaultwarden 容器、SQLite `quick_check`、完整 `/data` tar+age 快照、Docker 启动命令、启动后主动探测首次成功、第二次连续成功确认、Docker 原生状态读取及健康检查总等待汇总、本地校验/清单加密/SHA256、GitHub 同步/推送/远端提交核验，以及总耗时。

**恢复：** GitHub 克隆与备份列表、age 解密和归档/SQLite 校验、恢复目标检查、恢复前停止容器、回滚快照加密与验证、生产数据替换、恢复后 Docker 启动命令、恢复后主动健康探测首次成功、连续确认及 Docker 原生状态读取；若发生回滚，还会记录停止、旧数据恢复、重新启动和回滚健康检查阶段。

**v1.4.4 主动健康探测：** 对于 Docker 配置为 `CMD /healthcheck.sh` 的 Vaultwarden 官方镜像，管理器在容器启动后直接执行 `docker exec <容器名> /healthcheck.sh`，每 2 秒探测一次，连续 2 次成功即确认应用就绪，默认最长等待 120 秒，单次探测另有 12 秒超时保护。这样可以避免被动等待 Docker 原生 Healthcheck 的 60 秒调度间隔。Docker 原生 Healthcheck 不会被修改，后续仍按镜像原有策略持续运行。若镜像使用非标准探针，则回退到 Docker 原生 Health 状态轮询。检查配置仍可使用 `docker inspect <容器名> --format '{{json .Config.Healthcheck}}'`。

进入菜单 `[07]` 后可查看最近 20 次操作、最近 30 次操作的阶段平均与最大耗时、指定运行 ID 的阶段明细，并导出 CSV。恢复总耗时扣除 `USER_WAIT`，并单独记录从停止服务到确认就绪的 `SERVICE_DOWNTIME`。

更新源码后可在 `[22]` 同步后台脚本。后续运行产生新的阶段记录，历史日志保留原有粒度。

### v1.4.4 健康检查耗时优化说明

你可能在 Docker Inspect 中看到：`Interval=60000000000`（60 秒）。这是 Docker 原生健康检查的调度间隔，不代表 Vaultwarden 本身需要 60 秒才能启动。v1.4.4 对官方 Vaultwarden `/healthcheck.sh` 使用主动探测，每 2 秒执行同一个检查脚本，要求连续两次成功后即确认应用就绪，最长等待 120 秒。单次探测有 12 秒超时、总等待上限为 120 秒。它不修改容器健康检查配置，也不关闭 Docker 原生探针。性能记录包含 `readiness_probe_first_success`、`readiness_probe_confirmation` 和 `docker_native_health_observation`；`*_health_check_wait` 标记为 `aggregate` 汇总行，不会与子阶段重复计入统计。

### v1.4.5 可靠性行为

- 每次备份有独立运行 ID 和 `/var/lib/vaultwarden-backup/runs/<运行ID>.env` 结果文件。退出码 `0` 表示成功，`75` 表示因并发锁而跳过，其他非零值表示失败。
- 菜单 `[19]` 只读取本次运行的结果文件，并要求本地校验、服务恢复和当前目标远端核验全部通过。锁忙或结果缺失时终止检查。
- 加密快照生成后立即检查 age 文件头和 SHA256。后续容器启动、健康探测、清单或远端同步失败时保留已生成密文；离线 age 私钥模式下，SHA256 不代表已实际解密验证。
- VPS 若配置了匹配的 age 私钥，本地解密验证只在 `/dev/shm` 是 tmpfs 且空间足够时运行；空间不足时会跳过，以免把解密后的完整 `/data` 写到持久磁盘。age 私钥仍建议离线保存。
- 覆盖或回滚生产数据前，按 `/data` 主机路径重新确认唯一容器并复核停止状态。状态不明、目标变化或多个容器共用路径时中止操作并保留回滚快照。
- 备份会检查数据盘、备份目录、Git 仓库和临时分区空间；恢复解密前扫描归档，拒绝路径穿越、链接、特殊文件、重复成员和 setuid/setgid 条目，并按归档展开大小检查暂存分区。
- 备份会在停容器前检测 `/data` 中的符号/硬链接、特殊文件和 setuid/setgid 文件权限；发现后会中止，避免生成恢复器拒绝处理的归档。
- 配置文件要求 root 属主和 `600` 权限；配置替换会同步临时文件与父目录后再原子重命名。

升级源码后运行菜单 `[22]`，同步 systemd 使用的后台脚本和恢复检查器。

## 18. 全局命令 vbm

菜单脚本更新时会安装 `/usr/local/bin/vbm`。首次配置或通过 `[22]` 同步脚本后，可从任意目录运行 `vbm`。

```bash
vbm
```

即可进入交互式菜单。普通用户执行时会通过 sudo 请求 root 权限。每次运行 `sudo bash ./run.sh` 时都会自修复这个全局命令。命令指向最初克隆的项目目录，请勿删除或移动该目录。

### 诊断报告无法生成时

```bash
ls -l /usr/local/sbin/vw-diagnose.sh
```

## 19. 历史备份管理：菜单 10

选择 GitHub、本地或 WebDAV 来源。GitHub 支持查看、标记永久保留、取消保留和删除当前分支文件。自动清理会跳过 `.keep` 标记对应的备份和部署清单。本地和 WebDAV 会直接列出备份组，输入编号后确认删除配套文件，输入 `0` 或直接按 Enter 返回。

**重要：** 从 Git 当前分支删除文件，不等于清除 Git 历史对象。仓库体积仍可能增长；项目不会自动执行 force push 或重写 Git 历史。

## 20. 部署清单（菜单 06）

每次备份会生成单独加密的脱敏部署清单，记录镜像、挂载、端口、网络及允许记录的非敏感配置。秘密环境变量值不会写入清单。灾难恢复时可用原 age 私钥查看，以便在新 VPS 的 1Panel 中手动重建应用。

## 21. 隔离恢复演练：菜单 09

使用选定备份在临时目录解密和检查，并尝试通过临时 Docker 容器启动恢复数据。临时容器使用隔离网络（`--network none`），不映射端口，不挂载生产数据目录，不影响现有 Vaultwarden。演练后清理临时容器和目录。结果保留在屏幕上，按 Enter 返回主菜单。

隔离演练能提高对归档和服务启动能力的信心，但仍不能替代一次真实的新 VPS 恢复及用户登录验证。

## 22. 备份策略（菜单 21）

可配置：

- 本地备份保留天数。清理前核验完整远端副本。
- 单个加密文件大小上限（默认不超过 90 MiB）。
- 磁盘最低可用空间阈值。
- GitHub 推送重试次数与等待时间。

Git 历史中的旧对象可能不随工作树清理而删除。普通 GitHub 仓库单文件限制和仓库体积需要持续关注。本项目针对小型 Vaultwarden 实例，不集成多 age 密钥、Restic 或 S3。

## 23. 恢复到原 VPS 或新 VPS

1. 保证 1Panel 中已有 Vaultwarden 应用，容器停止或可由管理器控制。
2. 从 GitHub 获取源代码和加密备份。
3. 使用创建该备份时的原 age 私钥解密；不能用新生成的私钥代替。
4. 选择正确的历史备份并完成 SHA256、age、tar 和 SQLite 检查。
5. 恢复前先生成当前 `/data` 的加密回滚快照。
6. 核对将被替换的容器和 `/data` 主机路径，并输入 `yes`（不区分大小写）。
7. 恢复后等待容器 running/healthy；失败时工具尝试回滚。
8. 人工使用原用户主密码登录，并检查密码库项目、附件、TOTP 和客户端同步。
9. 确认恢复成功前，不要删除回滚快照。
10. 新 VPS 使用新的 GitHub Deploy Key；age 公钥仍沿用旧备份对应的公钥。

Vaultwarden 备份不能恢复用户主密码明文，也不能代替用户保存 MFA 恢复码。

## 24. 诊断与常见问题

### 容器名变了

1Panel 重建容器后可能产生新的随机后缀。工具会按已确认的 `/data` 主机目录重新匹配。若目录改变或出现多个候选项，运行菜单 01 重新确认。

### 诊断菜单 20 报 chmod 找不到文件

v1.4.2 已修复该竞态。运行菜单 `[22]` 同步后台脚本后再试。

### 备份提示 age 私钥不在 VPS

可定期在 `[05]` 或 `[09]` 临时提供原私钥，分别验证密文或演练恢复。

### 通知失败

通知失败不会影响备份状态。在 `[18]` 检查通知类型、URL、Token 和接收端可达性。分享日志前移除敏感内容。

### GitHub 推送失败

检查 SSH Deploy Key 是否添加到正确的备份仓库、是否勾选写权限、仓库地址/分支是否正确、GitHub 是否可达，以及单文件大小限制。

## 25. 安全与隐私

- 源码仓库与备份仓库分开；备份仓库必须 Private。
- age 私钥离线保存至少两份；丢失后无法解密对应备份。
- GitHub SSH Deploy Key 只负责仓库身份认证，age 密钥负责数据加密，二者用途不同。
- 不要提交 `/etc/vaultwarden-backup.conf`、SSH 私钥、age 私钥、Token、数据库、附件或 `.age` 文件。
- 不要在公开 Issue 中发布完整诊断报告，分享前需检查主机名、路径、域名和仓库账号。
- 恢复、删除和清理均需认真核对目标；建议先在非生产环境演练。

## 全局命令与启动自动检查更新

首次运行 `sudo bash ./run.sh` 时，程序会自修复全局命令 `/usr/local/bin/vbm`。之后在任意目录运行 `vbm` 即可打开菜单。如果提示找不到命令，返回项目目录执行 `sudo bash ./run.sh`，确认输出“全局命令已就绪：vbm”，再执行 `hash -r` 和 `vbm`。

交互式启动或选择 `[23]` 时会检查源码仓库的 `main` 分支。管理器检查工作区、目标版本和快进关系，用户输入 `yes` 后才更新源码并同步后台脚本。旧配置中的 `UPDATE_CHANNEL` 会被忽略。

终端菜单采用 Python 标准库计算中文全角字符的显示宽度，固定宽度绘制边框；标题下方显示 `Powered by OmenTwwnmfm`。


### 性能文件为空时的排查（v1.4.2 及之后版本）

如果 `[07]` 显示没有性能记录，可按以下步骤检查。

1. 确认当前项目源码已更新到最新版本。
2. 从 `vbm` 菜单执行 `[22]` 同步后台脚本。
3. 再执行一次菜单 `[02]` 手动备份。v1.4.2 的菜单 `[02]` 会优先使用当前项目目录内的 `scripts/vw-backup.sh`、`scripts/vw-common.sh` 和 `scripts/vw-manifest.py`，不会误调用旧版 `/usr/local/sbin/vw-backup.sh`。
4. 查看 `/var/log/vaultwarden-backup.log`，应出现 `[性能] 已启用阶段耗时记录`、多条 `[耗时]`，以及 `Performance records: /var/lib/vaultwarden-backup/performance.tsv`。
5. 检查文件：`ls -l /var/lib/vaultwarden-backup/performance.tsv`，并查看末尾：`tail -n 20 /var/lib/vaultwarden-backup/performance.tsv`。
6. systemd 自动任务使用 `/usr/local/sbin/vw-backup.sh`。升级后可用 `[22]` 同步新版脚本。

性能记录初始化/写入失败只会产生警告，不应导致备份或恢复失败。记录文件默认权限为 `600`，目录为 root 专用。

### 确认输入的大小写

所有风险确认统一接受 `yes`、`YES`、`Yes` 等大小写形式。只有完整输入单词 `yes` 才会继续；输入 `y`、空值或其他文字均取消。这样既避免误操作，也不再要求用户必须使用大写。

## 本地备份管理

默认 `BACKUP_DIR` 为 `/var/backups/vaultwarden`。菜单 `[11]` 按备份组显示文件名、文件数量、合计大小、类型、配套状态和保护状态。

| 文件 | 内容 |
|---|---|
| `vw-时间.tar.gz.age` | 完整 `/data` 常规加密快照 |
| `pre-restore-时间[-进程号].tar.gz.age` | 恢复前生成的当前数据快照 |
| `vw-时间.manifest.json.age` | 加密部署清单 |
| `.sha256` | 同名密文的 SHA256 校验文件 |
| `.keep` | 保留保护标记 |

在 `[11]` 输入备份编号、核对文件名并输入 `yes`，可删除该组密文、SHA256 和配套清单。带保护标记的组会被拦截。删除过程持有备份共用锁，并检查备份目录与数据、Git 工作目录的重叠关系。缺失归档的残留配套文件也会单独列为配套缺失组，可选中清理。

在 `[10]` 删除 GitHub 当前分支备份后，本地副本会保留，可通过 `[11]` 清理。Git 工作目录通常是 `/opt/vw-github-repo`。

在 `[05]` 验证本地备份，在 `[08]` 恢复生产数据。验证需要原 age 私钥，并执行 SHA256、age 解密、归档安全扫描和 SQLite `quick_check`。恢复保留确认、恢复前加密快照、容器停止复查与失败回滚步骤，支持旧版 `pre-restore-*` 文件。

## 独立 WebDAV 备份与恢复

已配置 GitHub 的实例可通过 `[12]` 添加 WebDAV。首次向导 `[01]` 也支持直接选择 `webdav`，继续完成 age 公钥、容器和本地目录配置。

1. 在存储服务中创建专用备份目录，确认支持 `PROPFIND`、`GET`、`PUT`、`MOVE` 和 `DELETE`。
2. 在 `[12]` 输入完整 HTTPS URL、用户名及密码或应用密码。凭据在目录测试通过后保存至 `/etc/vaultwarden-webdav.json`，由 root 所有，权限为 `600`。
3. 使用 `[02]` 创建并上传新备份，或使用 `[13]` 上传已有本地密文。新建备份短暂停机生成完整 `/data` age 快照，启动并通过健康检查后上传。
4. 上传先写临时文件并 GET 回读计算 SHA256，通过后以禁止覆盖的 MOVE 发布。清单先于数据归档，数据 SHA256 最后发布。同名同内容可继续补传，同名不同内容会停止并显示错误。本地密文在失败后保留。
5. 在 `[05]` 选择 WebDAV 备份并提供原 age 私钥，验证 SHA256、age、归档结构和 SQLite 数据库。
6. 在 `[08]` 选择 WebDAV 备份恢复。当前 `/data` 会先生成本地恢复前快照，启动健康检查失败时尝试回滚。

HTTPS 证书使用系统信任库验证。WebDAV URL 应直接指向最终目录。程序拒绝重定向，并限定读取目录下符合备份命名规则的直接文件。远端 SHA256 校验文件必须且只能引用所选原始文件名。

`[14]` 将 `BACKUP_TARGET` 保存为 `github` 或 `webdav`。systemd 和 `[19]` 升级前保护使用该目标。`[02]` 可单独选择此次手动备份的目标。

WebDAV 上传成功后，过期清理只处理远端副本通过回读校验的本地常规备份，保留恢复前快照、待补传备份和带 `.keep` 标记的备份。用 `[11]` 手动清理本地备份，在 `[10]` 按编号删除 WebDAV 备份组。

## 备份签名与迁移

`[01]` 或 `[03]` 可初始化 `/etc/vaultwarden-backup-signing/backup` 和 `allowed_signers`。签名私钥权限为 `600`，用于签署备份与清单的 SHA256 文件。请离线保存可信签名者文件，在恢复主机上从离线副本安装。若需要保留原签名身份，也可离线备份签名私钥。age 解密私钥继续独立保管。

`[05]`、`[06]`、`[08]` 和 `[09]` 都会验签。对已知来源的无签名旧备份，界面提供逐次 `UNSIGNED` 确认。签名无效或签名者未知会中止。

## 备份执行与保留设置

设置保存在 `/etc/vaultwarden-backup.conf`。旧的 `BACKUP_TARGET` 会作为主目标的默认值。

| 配置 | 行为 |
|---|---|
| `PRIMARY_TARGET` | 定时备份和升级前保护的主目标。`github` 或 `webdav` |
| `SECONDARY_TARGET` | 次目标，默认为 `none`。主目标核验成功即可通过升级前保护，次目标失败会告警 |
| `RETENTION_DAYS` | 本地常规备份达到该天数且主目标有完整副本时才清理 |
| `WEBDAV_RETENTION_DAYS` / `WEBDAV_MIN_KEEP` | 默认关闭远端清理。启用后保留最近若干组可用备份，并要求确认匹配的本地副本 |
| `ALERT_MAX_BACKUP_AGE_HOURS` | 默认随每日、每周、每月分别为 36、192、768 小时 |
| `ALERT_MAX_DRILL_AGE_DAYS` | 隔离演练提醒阈值，默认 90 天 |
| `SNAPSHOT_MODE` | 默认 `stop`。可选 `online`，使用 SQLite `.backup`，打包期间附件可能变化 |
| `CONTAINER_MATCH` | 可选，按名称或镜像中的文本匹配自定义容器 |

待补传清单保存在 `/var/lib/vaultwarden-backup/pending/`。每次运行先按时间补传，每份密文均校验签名和远端副本。待补传备份和恢复前快照会跳过过期清理。GitHub 当前分支的备份可通过 `[10]` 单独管理。更换目标账号或备份目录前请先处理待补传队列。

`vbm status` 查看状态。`vbm backup`、`vbm restore`、`vbm verify`、`vbm drill` 打开对应交互流程。
