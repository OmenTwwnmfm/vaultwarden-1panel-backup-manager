# Vaultwarden 1Panel Backup Manager 完整使用手册

**版本：1.4.1**  
**平台：Ubuntu / Debian + 1Panel + Docker + Vaultwarden SQLite**

---

## 1. 项目职责

1Panel 负责 Vaultwarden 应用、Docker、域名、HTTPS 证书和反向代理。本工具负责检测正确的容器与 `/data` 数据目录、创建一致性备份、age 加密、GitHub Private 同步、恢复、诊断和 systemd 自动调度。

本工具不会安装/升级 Docker、1Panel 或 Vaultwarden，不会配置域名、HTTPS 或反向代理。

## 2. 系统要求

- Ubuntu / Debian，使用 systemd。
- Docker 由 1Panel 管理，当前 Vaultwarden 容器运行正常。
- Vaultwarden 容器内数据路径 `/data` 映射到主机目录。
- 使用 SQLite 数据库，主机数据目录内存在非空 `db.sqlite3`。
- root 权限。
- GitHub 源码仓库与 GitHub Private 备份仓库分开。

不支持 MySQL/PostgreSQL 外部数据库，也不适合非 `/data` 自定义布局。

## 4. 下载与启动

```bash
sudo apt update
sudo apt install -y git
sudo git clone https://github.com/OmenTwwnmfm/vaultwarden-1panel-backup-manager.git /opt/vaultwarden-1panel-backup-manager
cd /opt/vaultwarden-1panel-backup-manager
```

## 6. 首次配置：菜单 01

向导会依次进行：

1. 检查 Docker 命令可用性。
2. 搜索名称或镜像中包含 Vaultwarden 的容器。多个候选容器时要求人工选择。
3. 使用 `docker inspect` 读取容器内 `/data` 对应的主机路径。
4. 确认主机路径存在，且其中有非空 `db.sqlite3`。
5. 检查并按需安装 age、git、openssh-client、sqlite3、python3、logrotate 等备份工具；不会安装 Docker。
6. 创建 GitHub 专用 SSH Deploy Key，显示公钥供添加到备份仓库 Settings → Deploy keys，并勾选 Allow write access。
7. 使用旧 age 公钥或首次生成 age 密钥。若已有历史备份，必须输入创建历史备份时的原公钥。
8. 设置备份目录、Git 工作目录、保留天数、最大文件大小。
9. 显示配置摘要；核对容器、镜像、`/data` 主机路径、GitHub 仓库、age 公钥后输入大写 `YES`。
10. 保存 `/etc/vaultwarden-backup.conf`（权限 600）并安装后台脚本。

age 公钥可以保存在服务器。age 私钥必须离线保存至少两份并验证可读；日常自动备份不需要把私钥留在 VPS。

## 7. 立即备份：菜单 02

执行前会再次自动发现容器，并用已经确认的 `/data` 主机路径匹配实例。若 1Panel 重建应用导致容器随机后缀变化，但数据路径不变，会更新容器名；若数据路径发生改变或存在多个无法唯一确定的候选项，则停止操作并要求重新配置。

执行过程：

1. 检查容器状态、数据路径、SQLite 文件和可用磁盘空间。
2. 短暂停止 Vaultwarden，保证整个 `/data` 快照一致。
3. 执行 SQLite quick_check。
4. 打包整个 `/data`，通过 age 公钥加密。
5. 加密快照创建后立即尝试启动 Vaultwarden。
6. 验证密文非空、大小、age 文件头和 SHA256。
7. 生成脱敏部署清单并单独 age 加密。
8. 将数据备份、部署清单及校验文件提交到 GitHub。
9. 重试临时推送错误，并核验 GitHub 分支提交 ID。
10. 记录备份结果并发送可选通知。

自动任务没有 age 私钥时，不会执行实际解密验证，也不会声称已经验证恢复能力。请定期通过菜单 08/18 使用离线私钥完成验证。

## 8. 检查环境：菜单 04

检查当前容器与配置中记录的主机数据路径是否匹配，检查 `db.sqlite3`、age 公钥、GitHub SSH 私钥和仓库读取连接。检测到容器名变化时会按原 `/data` 路径更新记录。

## 9. 查看日志：菜单 05

显示 `/var/log/vaultwarden-backup.log` 最近 100 行。systemd 的服务日志另可通过：

```bash
journalctl -u vw-backup.service -n 100 --no-pager
```

## 10. 定时任务帮助：菜单 06

查看 systemd timer 使用说明。不要同时在 1Panel 计划任务、crontab 和 systemd 中配置同一备份任务，否则会重复执行。

## 11. 更新后台脚本：菜单 07

从完整项目目录运行更新。安装新版前会要求大写 `YES`。保留 `/etc/vaultwarden-backup.conf`、age 公钥、SSH Deploy Key、本地备份和 GitHub 历史。更新后建议先运行菜单 04 检查环境，再运行菜单 08 验证一个历史备份。

## 12. 验证历史备份：菜单 08

从 GitHub 选择历史 `.tar.gz.age`，在输入原 age 私钥路径后执行：

- SHA256 校验。
- age 实际解密。
- gzip/tar 归档读取与安全路径检查。
- 检查 `db.sqlite3` 是否存在且非空。
- 对解密数据库执行 SQLite `PRAGMA quick_check`。

验证完成后，临时解密文件应在受限临时目录中清理。私钥建议从离线介质临时提供，测试完成后删除 VPS 上的私钥副本。

## 13. systemd 自动备份：菜单 09–12

菜单 09 可设置每日、每周日或每月 1 日，以及 VPS 本地时间。默认每日 05:20。安装：

- `/etc/systemd/system/vw-backup.service`
- `/etc/systemd/system/vw-backup.timer`

Timer 使用 `Persistent=true`，VPS 关机错过计划后，在下一次启动时补执行。菜单 10 查看状态，11 暂停，12 恢复。

常用命令：

```bash
systemctl list-timers --all | grep vw-backup
systemctl status vw-backup.timer
systemctl start vw-backup.service
journalctl -u vw-backup.service -n 100 --no-pager
```

## 14. 通知：菜单 13

支持 Telegram、ntfy 和通用 Webhook，可分别开关成功/失败通知。凭据保存在 root 专用配置文件中，权限 600。通知发送失败只产生 WARN，不会把已经成功的备份改判为失败。

不要把 Bot Token、ntfy Token 或 Webhook URL 发到公开 Issue，也不要放进 README。

## 15. 更新前保护：菜单 14

在 1Panel 更新 Vaultwarden 前，先运行一份完整备份。只有工作器返回成功且 GitHub 远端提交核验通过，才建议继续应用更新。版本更新仍由 1Panel 执行，本工具不会升级 Vaultwarden。

## 16. 系统诊断：菜单 15

生成脱敏诊断报告，默认目录：

```text
/var/log/vaultwarden-backup-diagnostics/
```

文件名类似 `diagnosis-YYYYMMDD-HHMMSS-PID.txt`，权限为 600，目录权限为 700。报告包括：

- 系统命令可用性（Docker、age、Git、SQLite 等）。
- 配置存在状态和非秘密配置字段。
- Docker 容器列表与当前 Vaultwarden 目标发现结果。
- 数据目录磁盘空间、目录大小、数据库大小和 quick_check。
- systemd timer 与最近服务执行状态。
- 最近备份结果摘要和日志尾部。

报告不会输出 age 私钥、SSH 私钥、Bot Token 或 Webhook Token。分享报告前仍应人工检查主机名、路径、域名和 GitHub 用户名等环境信息。

## 17. 性能监控与执行耗时分析：菜单 20

性能记录保存在：

```text
/var/lib/vaultwarden-backup/performance.tsv
```

文件由 root 创建，权限为 600，目录权限为 700。性能记录不包含密码、Token、私钥或数据库内容。

目前记录以下阶段：

**备份：** 容器发现与预检查、部署清单生成、停止容器/SQLite 检查/tar+age 快照、容器重启与健康检查、本地校验/清单加密/SHA256、GitHub 同步/推送/远端提交核验，以及总耗时。

**恢复：** GitHub 克隆与备份列表、age 解密和归档/SQLite 校验、恢复目标检查、恢复前回滚快照、生产数据替换、容器启动与健康检查，以及总耗时。

进入菜单 20 后可以查看最近 20 次操作、最近 30 次操作的阶段平均/最大耗时、指定运行 ID 的阶段明细，并导出 CSV。分析时重点关注 GitHub 同步阶段（网络因素）与快照/恢复阶段（磁盘、CPU 和数据量因素）。总耗时包含交互式选择/确认的等待时间，分析性能瓶颈时优先比较各阶段耗时。

首次升级到 1.4.1 后，需要运行菜单 07 更新后台脚本；更新后执行一次备份或恢复才会生成性能记录。旧版本的历史日志不会自动补算阶段耗时。

## 18. 全局命令 vbm

菜单脚本更新时会安装 `/usr/local/bin/vbm`。首次配置完成或菜单 07 更新后台脚本后，在任意目录执行：

```bash
vbm
```

即可进入交互式菜单。普通用户执行时会通过 sudo 请求 root 权限。每次运行 `sudo bash ./run.sh` 时都会自修复这个全局命令。命令指向最初克隆的项目目录，请勿删除或移动该目录。

### 诊断报告无法生成时

确认后台诊断脚本已安装：

```bash
ls -l /usr/local/sbin/vw-diagnose.sh
```

从项目目录更新脚本：运行菜单 07，或：

```bash
install -o root -g root -m 700 scripts/vw-diagnose.sh /usr/local/sbin/vw-diagnose.sh
```

查看报告目录：

```bash
ls -lah /var/log/vaultwarden-backup-diagnostics/
```

## 19. 历史备份管理：菜单 16

可查看 GitHub 当前分支可见的备份，标记永久保留、取消保留或删除当前分支文件。自动清理会跳过 `.keep` 标记对应的备份和部署清单。

**重要：** 从 Git 当前分支删除文件，不等于清除 Git 历史对象。仓库体积仍可能增长；项目不会自动执行 force push 或重写 Git 历史。

## 20. 部署清单：菜单 17

每次备份会生成单独加密的脱敏部署清单，记录镜像、挂载、端口、网络及允许记录的非敏感配置。秘密环境变量值不会写入清单。灾难恢复时可用原 age 私钥查看，以便在新 VPS 的 1Panel 中手动重建应用。

## 21. 隔离恢复演练：菜单 18

使用选定备份在临时目录解密和检查，并尝试通过临时 Docker 容器启动恢复数据。临时容器使用隔离网络（`--network none`），不映射端口，不挂载生产数据目录，不影响现有 Vaultwarden。演练后清理临时容器和目录。

隔离演练能提高对归档和服务启动能力的信心，但仍不能替代一次真实的新 VPS 恢复及用户登录验证。

## 22. 备份策略：菜单 19

可配置：

- 本地及 Git 当前分支文件保留天数。
- 单个加密文件大小上限（默认不超过 90 MiB）。
- 磁盘最低可用空间阈值。
- GitHub 推送重试次数与等待时间。

Git 历史中的旧对象可能不随工作树清理而删除。普通 GitHub 仓库单文件限制和仓库体积需要持续关注。本项目针对小型 Vaultwarden 实例，不集成多 age 密钥、Restic 或 S3。

## 23. 恢复到原 VPS 或新 VPS

1. 保证 1Panel 中已有 Vaultwarden 应用，容器停止或可由管理器控制。
2. 从 GitHub 获取源代码和加密备份。
3. 使用创建该备份时的原 age 私钥解密；不能用新生成的私钥代替。
4. 选择正确的历史备份并完成 SHA256、age、tar 和 SQLite 检查。
5. 恢复前先生成当前 `/data` 的加密回滚快照。
6. 核对将被替换的容器和 `/data` 主机路径，并输入大写 `YES`。
7. 恢复后等待容器 running/healthy；失败时工具尝试回滚。
8. 人工使用原用户主密码登录，并检查密码库项目、附件、TOTP 和客户端同步。
9. 确认恢复成功前，不要删除回滚快照。
10. 新 VPS 使用新的 GitHub Deploy Key；age 公钥仍沿用旧备份对应的公钥。

Vaultwarden 备份不能恢复用户主密码明文，也不能代替用户保存 MFA 恢复码。

## 24. 诊断与常见问题

### 容器名变了

1Panel 重建容器后可能产生新的随机后缀。工具会按已确认的 `/data` 主机目录重新匹配。若目录改变或出现多个候选项，运行菜单 01 重新确认。

### 诊断菜单 15 报 chmod 找不到文件

v1.4.1 已修复：先同步创建并设置报告文件权限，再启动 `tee`，避免进程替换异步创建文件引发竞态。运行菜单 07 更新后台脚本后再试。

### 备份提示 age 私钥不在 VPS

这是正常的离线私钥模式。备份仍可使用公钥加密并推送，但不会声称实际解密已验证。定期用菜单 08 或 18 临时提供原私钥完成验证。

### 通知失败

通知失败不会影响备份状态。检查菜单 13 中的通知类型、URL、Token 和接收端可达性；分享日志前先移除敏感内容。

### GitHub 推送失败

检查 SSH Deploy Key 是否添加到正确的备份仓库、是否勾选写权限、仓库地址/分支是否正确、GitHub 是否可达，以及单文件大小限制。

## 25. 安全与隐私

- 源码仓库与备份仓库分开；备份仓库必须 Private。
- age 私钥离线保存至少两份；丢失后无法解密对应备份。
- GitHub SSH Deploy Key 只负责仓库身份认证，age 密钥负责数据加密，二者用途不同。
- 不要提交 `/etc/vaultwarden-backup.conf`、SSH 私钥、age 私钥、Token、数据库、附件或 `.age` 文件。
- 不要在公开 Issue 中发布完整诊断报告，分享前需检查主机名、路径、域名和仓库账号。
- 恢复、删除和清理均需认真核对目标；建议先在非生产环境演练。

## 全局命令与启动自动检查更新

首次运行 `sudo bash ./run.sh` 时，程序会自修复全局命令 `/usr/local/bin/vbm`。之后在任意目录运行 `vbm` 即可打开菜单。如果提示找不到命令，返回项目目录执行 `sudo bash ./run.sh`，确认输出“全局命令已就绪：vbm”，再执行 `hash -r` 和 `vbm`。

每次交互式启动时都会检查公开源码仓库的最新提交。若发现更新，界面会显示远端版本，并等待输入 `yes`；其他输入均跳过。只有工作区干净且远端提交是本地提交的快进后继时才允许自动更新。systemd 备份不运行菜单，因此不会因更新提示而中断定时任务。菜单 `[21]` 可主动检查更新。

终端菜单采用 Python 标准库计算中文全角字符的显示宽度，固定宽度绘制边框；标题下方显示 `Powered by OmenTwwnmfm`。
